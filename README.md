# Auditing physical evidence in laboratory automation logs

**Research question:** To what extent can software-level laboratory actions be traced to independent evidence of their physical execution?

This repository reproduces a narrow audit of two public laboratory-automation datasets: a Chemspeed run from Flex-Cat and expert-labelled recoveries from a batch-distillation plant. It is the evidence layer for a separate article, not a general observability framework.

## Reproduced findings

Headline values are the committed invariants in [`data/manifest.json`](data/manifest.json) `expected_metrics`, regenerated by `scripts/reproduce.py`.

| Finding | Numerator | Denominator | Result |
| --- | ---: | ---: | ---: |
| Cleanly paired Chemspeed `type="operation"` events | 986 | 986 | 100% |
| Transfer endpoints where reported `actualVolume` equals requested volume | 60 | 60 | 100% |
| Labelled recoveries with ≥1 parseable operation-log timestamp in `[-60 s, +120 s]` | 34 | 79 | 43.04% |

The `actualVolume` result is an exact decimal comparison of a reported field. It does **not** establish that the value is an independent physical measurement. If the field is a controller or pump readback, its name alone does not tell a downstream consumer which evidentiary class it belongs to.

The 34/79 figure is an **observability/activity proxy**: at least one operation-log row with a parseable time of day falls inside the defined inclusive window. It is **not** evidence that the labelled physical or operator recovery action itself was observed. Absence of such a row is **not** evidence that no intervention occurred.

For Batch Distillation, the source metadata contains 81 labelled recoveries. Two belong to one experiment for which the pinned release has no operation-log file, so they are explicitly excluded. The analysed denominator is 79.

## Why the distinction matters

The audit keeps three records conceptually separate:

1. a requested software action;
2. controller or device readback, when that semantic origin is established;
3. independent evidence of physical execution.

A completed command can coexist with incomplete physical-effect evidence. Conversely, absence of a matching log event does not prove that the physical action did not occur.

Keep `RecoveryLabel`, `RecoveryEvidence`, and `RecoveryOutcome` distinct. The 43.04% figure counts labels that have *some* log activity nearby, not recovered outcomes.

## Reproduce the audit

Requires Python 3.12 and [uv](https://docs.astral.sh/uv/).

```powershell
uv sync --frozen --group dev
# Download the three pinned archives described in data/README.md.
uv run --frozen python scripts/reproduce.py
```

Expected final lines:

```text
Dataset verified
Actions parsed: 986
Labelled recoveries matched: 34 / 79
Metrics regenerated
Sensitivity analysis regenerated
Reproduction successful
```

Run the synthetic and committed-artifact checks with:

```powershell
uv run --frozen python -m pytest
```

Open the concise notebook with:

```powershell
uv run --frozen python -m jupyter lab notebooks/audit.ipynb
```

## Dataset provenance

Raw archives are intentionally not committed. Exact release identifiers, filenames, byte sizes, MD5, SHA-256, members used, and third-party licences are pinned in [`data/manifest.json`](data/manifest.json). Acquisition and attribution are in [`data/README.md`](data/README.md).

## Method

- Chemspeed operation identity is `(application_epoch, operationid)` and applies only to events with `type="operation"`. Start and end counts are replayed chronologically; only exactly one start plus one end is `clean`.
- Transfer endpoints are paired positionally within `src` and `dest`, because endpoint `id` is not unique in the source. Volumes are compared as `Decimal`, not binary floats. Endpoints missing requested or reported volume are excluded from the 60/60 comparison and counted separately.
- Batch Distillation recovery annotations are deduplicated by `(experiment, class, anomaly_id)`. The anchor is the unique perturbation end, with the unique anomaly end as an explicit fallback.
- Coverage means at least one raw operation-log row has a parseable time inside the inclusive window. It is not a claim that the row is a human recovery action, and it is not a claim that physical recovery occurred.
- Records remain in source order. Inputs are verified (size, SHA-256, and MD5) before parsing, and outputs contain no run timestamp or random identifier.

The sensitivity analysis compares `[-60 s, +120 s]`, `±300 s`, and `±600 s`. See [`results/window_sensitivity.csv`](results/window_sensitivity.csv). Wider windows can capture unrelated plant or UI activity.

## Limitations

- The Flex-Cat result covers one deposited Chemspeed run, not laboratory automation in general.
- Time-of-day matching does not infer midnight rollover; no analysed recovery window crosses midnight.
- Wider windows can capture unrelated activity. Sensitivity measures robustness to window width, not causal attribution.
- The 60 transfer rows were generated by deterministic parsing and comparison. No separate manual-adjudication file was recovered.
- Public CI uses synthetic fixtures because the upstream archives are not redistributed in this repository. Full reproduction requires the pinned inputs. A green CI run does not mean the real-data audit was re-executed.
